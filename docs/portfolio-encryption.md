# 资产数据加密与上线

持仓（标的、名称、数量、成本、币种）、现金、资产历史金额和目标仓位使用 AES-256-GCM 加密；每次随机 12 字节 IV。认证附加数据绑定用途、用户、账户及历史日期，密文带 `v1:` 版本前缀。密钥沿用服务器 secret `CREDENTIALS_KEY`，不存数据库，不返回客户端。密码仍使用加盐 PBKDF2；券商凭据的既有密文保持兼容。

库内保留账户归属、记录数量和历史日期等索引信息。旧数量/金额列在写入密文时同步置零，标的等文本置空；现金的旧币种索引替换为随机标识。SQL 导出不能直接读出这些资产字段，但服务端持有密钥，正常 API 仍需解密后返回本人。自选 `items`（含从持仓补入自选的标的）、账户名称、AI 对话不属于本次加密范围；公开自选看板仍按原有产品行为展示。

## 部署顺序

1. 确认目标 Worker 已配置并安全备份原有 `CREDENTIALS_KEY`（base64 随机 32 字节）。已有券商/AI 密文时必须沿用原密钥，不能随便生成新值覆盖。新环境才用 `wrangler secret put CREDENTIALS_KEY` 写入新随机密钥。
2. 先在目标数据库执行 `migrations/2026-10-20-portfolio-encryption.sql`。该 SQL 仅增列，不清除旧数据；已执行过不能重复执行。新建库直接用最新 `schema.sql`。
3. 部署新版 Worker。新写入只存密文；旧行暂时兼容读取，以保证滚动上线。缺失/错误密钥或损坏密文返回 503，不回退到零值、空持仓或明文写入。
4. 运行回填脚本直到 `remaining=0`：

```sh
# 本地：自动从被 Git 忽略的 .dev.vars 读取站长密码。
node scripts/encrypt-portfolio.mjs

# 线上：ADMIN_PASSWORD 通过安全环境注入；不要把密码放到命令参数里。
node scripts/encrypt-portfolio.mjs --url=https://your-site
```

脚本调用站长鉴权的 POST `/api/owner/portfolio/encrypt`，每批最多 50 行，只输出计数。每批先验证已有密文能用当前密钥解开，再加密旧行；加密和清除明文字段在同一 D1 batch 事务提交。重复运行安全，失败可重试；并发新版写入已加密的行不会被回填覆盖。

5. 用计数确认四张表 `data_enc IS NULL` 都为零，再验证汇总、CSV、券商同步与资产历史。未运行回填前，不能宣称历史数据已经全部加密。

回填不会抹除此前的 SQL 导出、数据库历史恢复点或备份中的明文；按实际备份保留策略处理。不要回滚到旧 Worker：旧代码不理解密文占位字段。密钥遗失无法恢复密文，轮换密钥需要单独的解密再加密迁移。

## 浏览器

资产页仅在当前页面内存保留数据，停止 `sessionStorage` 明文持仓/历史缓存，并在打开资产页时删除旧的 `pf_cache_*` 缓存。API 设置 `Cache-Control: no-store`。这不会把网站变成端到端加密，也不能防止已控制客户端或服务器的攻击者读取正在使用的数据。
